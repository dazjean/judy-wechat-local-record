# 场景包如何积木式落地

**日期：** 2026 年 8 月 29 日  
**状态：** 已确认（一期仍内嵌客服口径，不拆 `packs/`；销售/个人包立项时按本文抽协议）  
**确认：** 2026-08-29  
**关联：** [多场景扩展原则.md](./多场景扩展原则.md)

> 结论先说：**不是三套独立应用，也不是设置页切换。**  
> 一个进程、一套表、一个前端壳；场景包是实现同一协议的代码模块。装机时用环境变量绑死一个包，用户看不见切换。

---

## 1. 不做切换时，包怎么「装上」

界面不提供场景下拉。绑定发生在**进程启动**：

```text
.env / 启动脚本     LINGXI_SCENARIO=cs
        │
        ▼
   pack_loader.load()   只加载这一个包
        │
        ▼
   FastAPI / Vue 整次运行都问这一个包要规则和文案
```

| 交付形态 | 怎么绑 | 用户侧 |
|---|---|---|
| 庆总一期 | `.env` 写死 `cs`，或代码默认 `cs` | 就是现在这套客服中台 |
| 以后卖给销售团队 | 同一仓库，启动脚本改成 `LINGXI_SCENARIO=sales` | 菜单和雷达变了，没有「切回客服」按钮 |
| 个人版 | `personal` + 可关掉诊断页 | 像另一个产品，其实是同一套可执行文件 |

同一台电脑若真要两套场景：两份目录、两份库、两个端口，不要同一 `lingxi.db` 热切换。超时和雷达语义不同，混在一个库里会串。

---

## 2. 场景包是独立模块，但不是独立系统

| 做法 | 要不要 |
|---|---|
| `packs/cs`、`packs/sales`、`packs/personal` 三个目录 | 要 |
| 三个 git 仓库、三套 SQLite 表结构、三套同步代码 | 不要 |
| 包与包互相 import | 不要 |
| 基座 import `packs.cs` 写死 | 不要（只允许 loader 按 id 取包） |
| 微服务 / 插件市场 / 运行时热插拔 | 不要 |

积木是「基座砖 + 场景砖」，不是「三个房子」。

```text
                    ┌─ packs/cs        雷达SLA · 禁用词 · 客服诊断提示词 · 文案
  启动时只选一块 ───┼─ packs/sales     漏斗雷达 · 跟进超时 · 促单提示词
                    └─ packs/personal  欠回复 · 弱考核 · 可关诊断

  下面永远只有一块基座
  ingest · models · 会话页 · 导出 · 设置里的模型 Key
```

---

## 3. 基座稳定靠什么：一份小协议，而不是抽象一切

基座只依赖场景包的**接口**，不依赖某个包的词表。建议把协议收得很窄（先这些就够三包）：

| 积木槽 | 基座提供什么 | 包填什么 |
|---|---|---|
| 身份文案 | 消息角色仍是本机/对端 | `self_label` / `peer_label` / `product_name` |
| 导航 | 路由和页面壳已经在 | 哪些菜单显示、标题叫什么 |
| 超时 | `timeout_seconds` 配置项、响应时差算法（对端→本机） | 默认秒数；个人包可以默认 86400 |
| 雷达 | `GET /radar`、联系人循环、点进会话 | `classify`：状态、诉求、标记、排序、KPI |
| 词表 | `lexicon` 表、`hit_records`、扫描任务 | 默认词条、有哪些 `kind`；个人包可空 |
| 诊断 | 任务编排、调客户模型、结果 JSON 落库 | `system_prompt`；个人包可 `analysis_enabled=False` |
| 效率页 | 中位回复、时段分布 | `metrics_enabled`；个人包可关 |

基座**禁止**再出现「客服超时 180 秒」这种业务句子；那句话属于 `packs/cs`。

雷达行建议用**共享 DTO + 可选扩展**，避免每个包一张表：

```text
必有：contact_id, conversation_id, contact, status, status_label,
      snippet, last_msg_at, flags[]
可选：intent, 以及 flags 里包自定义的 tag（已发未回、决策卡点…）
前端：认识的 tag 画标准标记；不认识的当普通 pill，基座页面不用改
```

新场景若需要全新页面（例如销售漏斗看板），那是**新基座砖**，不是在包里复制一套 Conversations.vue。先问：现有雷达 + 筛选是否够用。

## 4. 目录怎么落到本仓库（对照现状）

当前客服口径散在这些文件里，以后整包搬走，基座只留调用：

| 现在 | 以后属于 |
|---|---|
| `engine/radar.py` 里的状态/诉求/风险词 | `packs/cs` |
| `analyze/prompt.py` | `packs/cs` |
| `MainLayout.vue` 品牌名和菜单字 | 包的 `labels` + `nav`，壳还在基座 |
| `metrics.py` 对端→本机时差 | **留基座**（销售/个人同样要「多久没回」） |
| `ingest/` 同步、解析、去重 | **留基座** |
| `models.py` 消息表 | **留基座**（字段名暂不改） |
| `Conversations.vue` / `Sync.vue` | **留基座**（角色文案走包） |

目标结构（销售/个人目录先不建）：

```text
backend/app/
  ingest/              基座
  models.py            基座
  engine/metrics.py    基座（通用响应）
  packs/
    protocol.py        协议
    loader.py          读 LINGXI_SCENARIO，只实例化一个包
    cs/                一期把现有雷达+提示词挪进来
```

前端一个壳：`GET /api/runtime` 返回产品名、菜单、角色名、功能开关。`MainLayout` 按菜单渲染，不要三份 layout。

## 5. 怎样保证复用，又怎样扩展

**复用（开闭：加包不必改同步）：**

1. 基座测试用一个 `FakePack`（固定返回两条雷达），不测客服词表。
2. 客服包测试继续用现在的 `test_radar.py` 夹具，只改 import 路径。
3. 新包 = 新目录实现协议 + 自己的单测；`ingest` / `models` / 会话 API 零改动。
4. 包禁止访问微信读取、禁止自己建消息表。

**扩展（基座也要长，但长一次、三包受益）：**

| 需求 | 加在哪 |
|---|---|
| 销售要「已发未回」 | 包的 `classify`，基座雷达表已能展示未知 tag |
| 个人要隐藏效率页 | 包 `nav` / `metrics_enabled` |
| 三种场景都要更好的公众号过滤 | **改基座** `review.py`，包自动受益 |
| 销售要独立漏斗页，雷达真不够 | 基座加一页，包决定显不显示 |
| 第四个行业包（教培以外） | 新 `packs/xxx`，仍不要 fork 仓库 |

判断口诀：差异是**规则和文案** → 进包；差异是**读库、同步、页面壳** → 进基座。拿不准时先进包；发现三包复制同一段 Python，再抽回基座。

## 6. 一期明确不搬代码

现在就把文件拆开，对庆总验收没有增量，还容易把同步拆坏。

一期编码约束（为以后搬家做准备）：

- 新逻辑按本机/对端写，不要再写「只有客服角色才算超时」这种假设。
- 不要复制 `Dashboard.vue` 去做「个人版首页」。
- 不要在设置页加场景切换。
- 真正做销售包的第一天：先抽 `protocol` + 把现有 `radar.py` / `prompt.py` 挪进 `packs/cs`，再写 `packs/sales`。
