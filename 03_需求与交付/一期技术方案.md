# 灵犀·客服数据中台 · 一期技术方案

**客户：** 庆总（AI题库 / AI校本业务）  
**依据：** `03_需求与交付/一期需求确认.md`  
**版本：** v1.5（多场景底座：一期仅客服包；对用户隐藏 wechat-cli）  
**日期：** 2026 年 8 月 29 日  
**设计原则：** 单机可交付、链路完整、规则与模型解耦、现场可改配置、不把数据带离客户环境。底座按「本机微信聊天台」设计，客服 / 销售 / 纯个人为可替换场景包；一期只启用客服包。详见 [多场景扩展原则.md](./多场景扩展原则.md)。  
**读取依据：** 灵犀 AI 帮聊已验证的本机读库方式，只复用「读」，不复用「发 / 监听 / 托管」。本期不做文件导入。  
**对外口径：** 产品只呈现「微信同步 / 微信读取初始化」；wechat-cli 仅为内部实现，对客户隐藏。

---

## 1. 设计目标

在 2～3 周、单机部署、¥8,000 一期范围内，做成可验收的「读取 → 整理 → 统计/分析 → 展示/导出」系统，而不是先堆后台框架。

三条硬约束：

1. **数据不出客户环境**（除客户自己配置的模型 API）；
2. **只读业务数据，不发送消息**；
3. **规则指标不依赖模型**，模型只负责归纳、摘要和建议，API 故障时效率统计仍可用。

产品线要能覆盖客服、销售、纯个人，但**不要做成三套同步系统**。采集与消息表是底座；雷达规则、默认超时、词表、提示词、界面名词是场景包。一期交付并验收的只有客服包。库字段暂保持 `cs` / `customer`（本机 / 对端的客服叫法），新逻辑按本机/对端理解，避免再写死「只有客服场景才成立」。

## 3. 技术选型

| 层 | 选型 | 原因 |
|---|---|---|
| 语言 | Python 3.11+ | 解析、统计、调模型、本地脚本同一语言，现场改配置成本低 |
| API | FastAPI + Uvicorn | 接口清晰，适合把分析任务做成异步接口 |
| ORM / 库 | SQLAlchemy 2 + SQLite | 单机零运维；库文件可随电脑备份；体量超出后再迁 PostgreSQL |
| 前端 | Vue 3 + Vite + Element Plus | 管理页开发快，交付后客户侧也常见、好改 |
| 表格导出 | openpyxl | 筛选结果导出 Excel（不做文件导入） |
| HTTP 客户端 | httpx | 调 OpenAI 兼容模型接口 |
| 打包启动 | 启动脚本 + 前端 dist 内置 | 现场尽量「安装 Python 依赖后一键启动」；不强制 Docker |
| 微信读取 | 内嵌读取组件（内部为 wechat-cli） | 直读本机库，不占微信 UI；**对用户隐藏组件名与控制台** |
| 可选 | Windows 任务计划 | 仅当客户需要定时增量同步时启用，不做复杂队列中间件 |

不引入 Redis、Celery、Nginx、独立用户中心。一期用进程内后台任务即可：微信同步、词表扫描、AI 分析都写成 Job，状态进库，页面轮询。

**操作系统与微信基线（对齐灵犀，待现场确认）：**

| 环境 | 基线 | 初始化 |
|---|---|---|
| Windows 10/11 x64 | 微信 PC **4.1.9.0** | 产品安装包内嵌读取组件；管理员跑「微信读取初始化」（内部调 init） |
| macOS Apple Silicon | 微信 **4.1+** | 同上；4.1+ 若 0 key 走灵犀同款适配器，客户界面仍只说初始化失败原因 |

读取组件装入产品自己的 venv/`vendor/`，**不写入系统 PATH**，客户不能从开始菜单搜到 wechat-cli。

## 4. 采集策略：wechat-cli 唯一来源

采集层只从本机已登录微信产出统一消息。**不做 xlsx/csv/json/txt 文件导入。**

一期单机一次只读 **当前登录的那一个客服微信号** 下的多个客户会话。多客服号、多台电脑归二期。

「微信读取初始化」失败时，P1 视为环境未就绪，不改其它取数通道。

### 4.1 统一消息（规范化后）

| 字段 | 含义 |
|---|---|
| `account_key` | 本机登录客服号的稳定标识（username / 展示名） |
| `peer_key` | 客户侧 username（优先）或备注名 |
| `conversation_key` | 会话标识；wechat-cli 按联系人维度，缺省用 `account_key + peer_key` 再按间隔切分 |
| `msg_time` | 消息时间（本地时区；CLI 常精确到分钟，缺秒补 `:00`） |
| `sender_role` | `cs` / `customer` / `system` |
| `msg_type` | `text` / `image` / `voice` / `file` / `system` / `other` |
| `content` | 文本正文；非文本用 `[图片]` `[语音]` 等占位 |
| `source_type` | `wechat_cli` |
| `source_ref` | 联系人 username + 时间 + 正文摘要，用于去重 |
| `raw_hash` | 去重键：账号 + 对端 + 时间 + 角色 + 正文哈希 |

### 4.2 wechat-cli 本机读取（对齐灵犀）

灵犀已验证：**读消息走 `wechat-cli history` 直读本地库，不占微信 UI。** 中台只复用这条读链路，落 SQLite，不写灵犀的按日 JSON，也不接发送/监听。

#### 4.2.1 与灵犀的取舍

| 能力 | 灵犀帮聊 | 本期中台 |
|---|---|---|
| `sessions` / `contacts` / `history` | 有 | **复用命令契约与解析** |
| 行解析、去 emoji、username 兜底、读锁 | 有 | **按同逻辑实现（独立模块，不依赖帮聊进程）** |
| 内容归一（XML → `[图片]` 等） | `wechat_content_normalizer` | **复用同一套规则** |
| 截图/视觉补全语音图片 | `message_enricher` | **不做**（一期分析以文本为主） |
| 发送、智能托管、自动回复 | 有 | **明确不做**（wechat-cli 本身也无发送能力） |
| 存储 | `chatlogs/<联系人>_YYYYMMDD.json` | **SQLite 统一消息表** |

#### 4.2.2 命令契约（与灵犀一致）

```text
wechat-cli sessions [--limit N]
wechat-cli contacts --query "<备注或昵称>"
wechat-cli history "<备注名或 username>" --start-time YYYY-MM-DD --limit N
```

`history` 成功时 stdout 为 JSON：`{ "messages": [ "行", ... ] }`。  
单行格式（灵犀 `TIMESTAMP_PATTERN`）：

```text
[YYYY-MM-DD HH:MM] 发送者: 正文
[YYYY-MM-DD HH:MM:SS] 发送者: 正文
```

角色映射（与灵犀 `SELF_MARKERS` 一致，语义改成客服）：

- 发送者为 `me` / `我` / `自己` → `sender_role = cs`（本机登录号即客服）
- 发送者为 `[系统]` → `system`，统计时默认跳过
- 其余 → `customer`（私聊为客户；群聊保留 `sender` 显示名）

Windows 调用对齐灵犀 B36：`PYTHONIOENCODING=utf-8`、**必须隐藏控制台黑窗**、只用产品包内绝对路径，不依赖 PATH 上的 `wechat-cli`。

#### 4.2.3 同步流程

1. 探测 CLI：能执行且 `sessions` 返回 JSON，视为已初始化。
2. 用 `sessions`（必要时补 `contacts`）得到会话列表；跳过文件传输助手等系统会话。
3. 对每个联系人拉 `history`（`--start-time` 用上次成功同步日或用户选定的起始日，`--limit` 默认 1000～3000，与灵犀回填同量级）。
4. 名称失败时按灵犀顺序降级：去 emoji 重试 → `contacts --query` 按备注/昵称打分 → 用 `username` 再拉，并缓存「显示名 → username」。
5. 解析行、内容归一、映射统一消息、按 `raw_hash` 去重写入。
6. 多联系人并行读库时加 **进程级读锁**（灵犀 `wechat_cli.lock`），避免同时打开本地库。
7. 任务页展示：联系人数、成功会话、写入条数、失败原因（用下表业务文案，不出现命令名）。

增量：每个 `peer_key` 记录 `last_synced_at`，下次只拉该日之后；全量重跑仍靠去重保证幂等。

#### 4.2.4 初始化（现场，对客户隐藏命令）

对客户只提供产品内按钮或 `微信读取初始化.bat`（UAC 显示「灵犀·客服数据中台」）。内部仍走灵犀同一套 init，密钥留在客户本机用户目录，**不进 Git、不进《使用说明》**。

- 微信须已安装并登录；版本过高导致读不到时，Windows 锁 **4.1.9.0**。
- 未打开微信、权限不足、微信更新后需重新初始化：故障处理写进《使用说明》的业务语言，以及仅实施人员可见的附录。

#### 4.2.5 对用户隐藏 wechat-cli（实现硬约束）

对应 NFR-09。内部可以叫 wechat-cli，**对外必须藏住**。

| 层 | 要求 |
|---|---|
| 界面 | 文案只用「微信同步」「微信读取状态」「初始化微信读取」。设置页、任务页、空状态均禁止出现 wechat-cli、canghe、huohuoer |
| 接口 | `/api/wechat/*` 的 `message` / `detail` 只返回中文业务句。日志可以写内部名，默认不给前端 |
| 进程 | Windows 对齐灵犀 `win_subprocess`：`CREATE_NO_WINDOW` + `STARTUPINFO.wShowWindow=SW_HIDE`；父进程用 `pythonw` 或产品 exe，同步时不闪黑窗 |
| 安装 | 组件打进 `vendor/` 或产品 venv，**不写入系统 PATH**，不建「wechat-cli」开始菜单项，不要求客户 pip/npm |
| 文档 | 《使用说明》零出现 wechat-cli；《部署说明》分客户步骤与「实施附录」，命令只在附录 |
| 快捷方式 | 桌面/开始菜单只有产品名 |

内部错误 → 对外文案：

| 内部情况 | 页面展示 |
|---|---|
| 组件未找到 / 未打包 | 微信读取组件未就绪，请重新安装本系统 |
| 未初始化 / 0 key | 尚未完成微信读取初始化，或当前微信版本不兼容 |
| 微信进程未运行 | 请先打开并登录微信，再点同步 |
| 读库超时 | 读取超时，请稍后重试 |
| 某联系人无历史 / 匹配失败 | 该会话暂无记录或名称无法匹配 |

探测接口对外字段建议：`reader_ready`、`wechat_logged_in`、`hint`，不要返回 `wechat_cli_path`、命令行。

#### 4.2.6 模块位置

独立目录 `ingest/wechat_cli/`（源码内部名可保留）：`runner.py`（定位组件 + 锁 + 编码 + **隐藏窗口**）、`history.py`、`contacts.py`、`parse.py`、`normalize.py`、`sync_job.py`、`errors.py`（内部异常映射成对外文案）。  
不启动灵犀 8787、不引用 `smart_chat`。解析与归一化以灵犀脚本为行为基准，保持本仓库可单独交付。

### 4.3 会话切分

优先级：同一联系人的 history 视为一条客户时间线 > 再按间隔切分。

默认：同一 `account_key + peer_key`，相邻消息间隔 **> 12 小时** 视为新会话。阈值可配置。

## 5. 数据模型

SQLite 单文件，建议路径：`data/lingxi.db`（客户可改）。核心表如下。

```text
accounts          客服账号（展示名、外部标识、来源）
contacts          客户（归属账号、外部标识、昵称/备注）
conversations     会话（账号、客户、起止时间、消息数）
messages          消息（会话、时间、角色、类型、正文、去重键、来源）
import_jobs       微信同步任务
sync_cursors      各联系人上次成功同步时间
analysis_jobs     AI 分析任务
rule_scan_jobs    词表扫描任务
metric_daily      按客服+自然日的效率快照
hit_records       禁用词/话术命中
analysis_results  AI 结构化结果（高频问题、未闭环、建议等）
settings          超时阈值、会话间隔、模型 endpoint、模型名等
lexicon           词表（类型=forbidden/script，词条、启用状态）
```

`messages.source_ref + raw_hash` 建唯一索引，保证重复同步幂等。

配置中的 API Key **不进业务库明文展示**，写入客户本机 `.env` 或系统用户目录下的本地配置文件，权限仅当前系统用户可读。页面只显示「已配置 / 未配置」，不回显完整 Key。

## 6. 规则引擎

对应 FR-11～FR-17。全部在本地算，不调用模型。

### 6.1 响应与超时

对每个会话按时间排序后扫描：

- **待回复点：** 客户文本消息，且其后尚未被客服回复覆盖；
- **首次响应：** 会话内第一条客户有效消息 → 其后第一条客服消息；
- **平均响应：** 所有「客户消息 → 下一条客服消息」时差的平均；客服连续发言不重复计；
- **超时未回：** 时差 > `timeout_seconds`（默认 180），或直到统计时刻仍无回复且已超时；
- 系统消息、纯表情占位、非文本是否计入，做成配置，默认：仅 `text` 计入响应统计。

结果写入 `metric_daily`，并保留会话级明细，供页面下钻到具体超时消息。

### 6.2 词表扫描

- 禁用词、基础话术分两张逻辑词表，支持子串匹配；需要时可对单条启用「整词」；
- 只扫 `sender_role = cs` 的文本；
- 命中写入 `hit_records`（词条、消息 ID、会话 ID）；
- 词表变更后对选定范围重跑扫描，不必重导数据。

客户未提供词表时，内置一小份可编辑示例（如绝对化承诺、辱骂、竞品贬低等占位），上线前用客户正式词表替换。

### 6.3 好友雷达

对应 FR-38。全部在本地算，不调用模型，不落雷达结果表。

- 分析对象是**联系人**，不是切分后的单段会话；打开或刷新页面时当场计算；
- 剔除公众号/系统会话（与明细同一套 `contact_is_official`），并排除 `@weclaw`；
- 顶栏日期只决定「名单里有谁」（范围内至少一条消息）；状态、诉求、风险、超时、承诺仍按该客户全部已同步消息；
- 状态四选一：待回复 → 沉寂（≥7 天）→ 新询盘（客户文本 ≤3 且跨度 ≤7 天）→ 跟进中；超时未回是待回复上的标记，阈值同 `timeout_seconds`；
- 主诉求、风险、承诺未兑为子串规则；禁用词读 `hit_records`（同步成功后扫描或效率页重跑，打开雷达不重扫词表）；
- 客服包增补：身份倾向（机构/家庭/个人）、已发未回、决策中、退费前兆、老客（≥30 天）；
- 接口 `GET /api/radar`；页面点行跳转 `/conversations?id=<最近会话>`。

完整口径与验收见 [FR-38-好友雷达.md](./FR-38-好友雷达.md)。

## 7. AI 分析引擎

对应 FR-18～FR-24。模型由客户提供，费用客户自担。

### 7.1 接入方式

按 **OpenAI 兼容 Chat Completions** 实现（`base_url` + `api_key` + `model`）。豆包、DeepSeek、通义等兼容网关均可。若客户接口不兼容，再加一个适配器，不改分析编排。

调用原则：

- 仅分析任务触发时出站；
- 超时、429、5xx 可重试（有限次）；单会话失败记录原因，不让整批任务失败到零结果；
- 记录大概 token 用量到 `analysis_jobs`，便于客户感知费用，不做计费系统。

### 7.2 两段式分析

**第一段：会话级（对每个需关注会话）**

输入：会话元信息 + 文本消息时间线（过长则截断首尾 + 中间摘要策略，优先保证最后 20～30 轮）。

要求模型只返回 JSON，例如：

```json
{
  "summary": "一句话摘要",
  "topics": ["课时包", "退费"],
  "unresolved": true,
  "unresolved_reason": "客户追问退费规则，客服未给出明确口径",
  "repeated_ask": true,
  "risk_note": "",
  "need_attention": true,
  "attention_reason": "重复追问且超时"
}
```

**第二段：范围级汇总**

输入：该范围的规则指标（响应/超时/禁用词）+ 会话级 JSON 列表（可抽样高频会话，避免超上下文）。

输出：高频问题（问题、频次/占比、代表会话）、未解决列表、重复追问列表、分客服建议。

页面展示以第二段为主，会话级结果用于下钻。提示词写成独立模板文件（`prompts/`），便于按客户话术规则改，而不改代码。

### 7.3 任务编排

1. 用户选定账号 + 时间范围，创建 `analysis_job`；
2. 若该范围规则指标未算过，先跑规则引擎；
3. 筛选「有客户文本」的会话，可设上限（如单次最多 200 个会话），超出则提示缩小范围或分批；
4. 并发度默认 1～3，避免打爆客户账号限流；
5. 状态：`queued / running / partial_failed / succeeded / failed`；
6. 同一范围允许重跑，新结果覆盖展示并保留任务历史。

模型未配置时，效率与词表页仍可用，分析页明确提示「请配置模型 API」。

## 11. 部署与运行

### 11.1 推荐形态

指定电脑安装本产品（Windows 用项目 venv / 启动包）。前端可预构建，现场只起 API。

客户侧启动前：

1. 安装并登录约定版本的微信 PC；
2. 以管理员运行产品提供的「微信读取初始化」（不要让客户自己敲内部命令）；
3. 打开本机页面，看「微信读取状态」为就绪后，点「同步」。

实施人员在附录中自检读取是否成功；客户《使用说明》只写上述三步。

然后再配置模型 API（页面或 `.env`），启动产品。

数据文件、日志、导出文件放在 `data/`、`logs/`、`exports/`，与源码分离，便于备份且避免误提交客户数据。

### 11.2 安全

- 默认只监听 `127.0.0.1`，防止同网其他机器直接打开；
- `.env` 与本机读取密钥不进源码和客户文档；
- 同步默认关闭自动轮询，由页面按钮或约定定时任务触发，避免后台长时间占库；
- 读取组件不进系统 PATH、不弹控制台；
- 不做我方云同步、不做隐式遥测。

### 11.3 备份

告知客户：备份 `data/lingxi.db` 即可迁业务数据。换电脑后须在新环境重新做「微信读取初始化」，密钥不能当通用许可证拷贝滥用。

## 13. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 微信版本不是 4.1.9.0 / 4.1+，初始化得到 0 key | **无法取数，P1 阻塞** | 现场锁灵犀已验证版本；协助「微信读取初始化」；不改文件导入 |
| 联系人重名、emoji、history 匹配错人 | 串会话 | 复用灵犀：去 emoji、`contacts --query`、username 缓存 |
| 同时拉多个会话打库 | 超时或空结果 | 全局读锁串行读 |
| 时间戳只到分钟 | 去重/响应口径偏差 | 与灵犀相同：缺秒补 00；去重以内容+时间窗口为主 |
| 同步时弹出控制台 / 客户看到 wechat-cli | 体验与交付口径不符 | 按 4.2.5：隐藏窗口、不进 PATH、界面与使用说明禁名 |
| 历史量过大 | 同步过慢 | 默认近 7～30 天、每联系人 limit；全量历史另行评估 |
| 模型接口不兼容或限流 | AI 页不可用 | OpenAI 兼容优先；规则指标独立 |
| 统计口径与客户体感不一致 | 复盘不认可 | 阈值可配；超时列表下钻到原消息 |

## 14. 与二期的衔接（本期不做）

一期把「账号、客户、会话、消息」留在本地库。二期多设备上报时，客服电脑仍用本期本机微信同步，只增加增量上报（`raw_hash`），中心后台复用同一套消息字段。

评分、画像、日报等不在本期预埋复杂表结构，避免空设计。`analysis_results` 用 JSON 载荷即可扩展。

销售包、个人包不在本期实现：不预埋空的场景配置表、不上线场景切换。积木式落地（启动绑定 `LINGXI_SCENARIO`、`packs/` 协议、一期不拆目录）已于 2026-08-29 确认，见 [场景包积木式落地.md](./场景包积木式落地.md)。需要时先抽协议再写新包，复用本期消息模型。
